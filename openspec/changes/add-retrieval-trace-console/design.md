# Design

## Context

`retrieval_runs` 与 `retrieval_hits` 已在每次检索时写入（含 `search_mode`、`candidate_count`、`rerank_model`
以及 `vector_score` / `fulltext_score` 与 `stage` 区分）。检索器 `engine/rag/retriever.go` 已支持逐请求覆盖
`rerank` 开关，融合在服务端完成，因此"换参数再查一次"不需要改检索实现。
约束：`backend/AGENTS.md` 的分层与"阈值/降级必须可见"的既有约定；前端遵循 `web/AGENTS.md` 的视觉方向。

## Goals / Non-Goals

- Goals：让留痕可读、让参数可试错、让"为什么没搜到"能当场回答。
- Non-Goals：不做检索质量自动评估（标注集 / 命中率指标）；不做跨知识库对比；不改检索算法。

## Decisions

**D1 历史回看走只读接口，不重新检索**
理由：留痕的价值在于"当时就是这个结果"；重新检索会得到当前配置下的结果，无法解释历史现象。
被否方案：展开时实时重算——看起来更简单，但会误导排查方向。

**D2 召回测试复用现有检索入口，参数按请求覆盖**
理由：检索器已支持逐请求覆盖（如 `rerank` 三态），复用可以保证"测试结果"与"真实问答"同源，
避免出现两套行为不一致的检索路径。被否方案：为测试页写一条独立检索链路——短期快，长期会产生行为漂移。

**D3 临时参数显式不落库，且回显**
理由：召回测试是调试动作，写库会污染知识库配置；不落库就必须把"本次用了什么参数"标在结果上，
否则用户会把测试结果误当成默认配置的效果。

**D4 对比结果放内存态（前端），不建表**
理由：对比是临时视图，持久化没有明确用途；真要留存可以把结论写进 `docs/PROGRESS.md`。

**D5 限制测试频率与条数**
理由：每次测试都会真实调用 embedding / 重排，属于付费路径；界面按"每次一条查询 + 有限条数"约束，
不做批量压测（批量压测交给命令行）。

## Risks / Trade-offs

- [误以为测试参数已生效到知识库] → 结果区固定显示参数标签，并在设置页与测试页互相给出提示语
- [留痕表随时间膨胀] → 查询接口默认分页并限制时间范围；清理策略留给后续（本 change 不做删除功能）
- [对比视图信息过载] → 默认只展开分数与出处，正文按需展开（避免整页都是长文本）

## 迁移计划

纯增量：新增接口与页面，不改表结构、不改既有检索行为；回滚只需撤下页面与路由。

## Open Questions

- 留痕的保留期与清理方式（本 change 不做，实现时按"只读查询 + 分页"处理即可，不影响规格与任务）。
