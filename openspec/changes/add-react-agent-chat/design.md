# Design

## Context

当前对话链路是「固定 RAG」：`handler/chat.go` → `service/chat.go` → `engine/chat` 组装的 Eino Graph，
入口按应用形态过滤（`agent` / `workflow` 直接拒绝）。检索器 `engine/rag` 已经能按知识库配置返回带溯源的片段。
模型层已通过 `engine/model` 的接口访问，凭证与选型由 resolver 决策。
约束见 `backend/AGENTS.md`：模型必须经接口访问、错误必须向上传递、并发用 errgroup 收敛。

## Goals / Non-Goals

- Goals：让 `agent` 形态能用「检索」这一个工具完成多步问答，且过程对用户可见、可落库回看。
- Non-Goals：不做工具市场与动态安装（V2.0 插件市场）；不做多智能体分工；不引入新的检索实现
  （直接复用 `engine/rag` 检索器，含三种检索方式与重排配置）。

## Decisions

**D1 工具用「注册表 + 接口」而不是 if/else 分支**
定义工具接口（名称、描述、参数结构、执行方法），知识库检索作为它的第一个实现。
理由：V2.0 的工具生态要能「新增一个实现」而不是改核心流程（开闭原则，见根 `AGENTS.md` 第 10 节）。
被否方案：在 ReAct 循环里硬编码"检索"分支——短期快，长期每加一个工具都要动运行时。

**D2 工具集按「本次问答」组装，可为空**
证据：`apps` 表没有知识库绑定列（`0001_init.sql`），当前 RAG 问答的知识库来自请求参数
`service/chat.go` 的 `input.DatasetID`（RAG 形态必填）。因此智能体沿用同一形态：本次请求指定了知识库就注册检索工具，
没指定就不注册（但演示计算工具始终可用）。
理由：与既有实现一致，零数据模型改动；不注册比注册后返回空结果更诚实。
被否方案：新增 `apps.dataset_id` 绑定列——会把"智能体"与"知识库"强绑定，而现有 RAG 形态并不这样工作。

**D3 工具调用以独立事件流式返回，并落库**
沿用现有 SSE 事件风格，新增工具调用类事件（开始 / 结果）。事件与消息都保留工具名、入参与结果摘要，
但**结果正文截断**（只留摘要与引用），避免把整段知识库正文塞进消息表。
理由：V0.1 的目标是"可演示、可解释"，用户要能看到模型查了什么；同时表体积要可控。
被否方案：只记日志不落库——刷新页面就看不到推理依据。

**D4 工具执行失败不中断问答**
工具错误作为工具结果回灌给模型（模型可以换关键词重试或如实说明），同时把失败原因写进事件与留痕。
仅在模型调用本身失败时终止。
理由：检索偶发失败不应让整轮问答报废；但失败必须可见（不静默吞错）。

**D5 循环有轮次上限，默认 3 次（2026-10-12 用户拍板）**
工具调用轮次上限可配置，**默认 3**；达到上限时结束并返回已完成的内容 + 明确说明已达到上限。
被否方案：不限轮次——成本不可控，且模型可能陷入重复检索。

**D6 形态路由放在 service 层**
`service/chat.go` 按 `app.mode` 选择链路；`workflow` 仍返回明确错误。
理由：分层规则要求业务编排在 service，handler 只做参数与响应组装。

**D7 工具集含一个无副作用演示工具（2026-10-12 用户拍板）**
除知识库检索外，注册一个计算工具：不依赖任何外部服务、不写业务数据。
理由：知识库检索工具依赖向量库与向量化服务，一旦外部依赖出问题就无法判断"是工具机制坏了还是依赖坏了"；
一个纯本地工具能把这两个问题分开，同时给后续工具提供最小样板。
被否方案：只注册检索工具——演示与排障时缺少参照物。时间工具可选，本 change 不做。

**D8 工具调用默认展示、可关闭（2026-10-12 用户拍板）**
界面默认展示工具调用块，并提供关闭开关；关闭只影响展示，不影响执行与落库（否则"看不见"会变成"没发生"，排障时无从下手）。

**D9 检索范围沿用现状：一次问答最多一个知识库（2026-10-12 用户拍板）**
不新增应用级绑定，沿用请求参数（`input.DatasetID`）的形态，一次问答最多一个知识库；
但**工具的检索范围参数按列表设计**（`datasetIds`），当前只接受 1 个，传入多个**明确报错**而非静默取第一个。
理由：现状零改动即可落地（见 D2 的证据）；列表契约让多知识库放开时不用改工具契约、前端事件格式与工具描述。
被否方案：本 change 直接支持多知识库——跨库分数不可比（各库可能用不同向量模型、检索方式与阈值）、
TopK 在库间怎么分配、重复片段去重、引用是否带库名都会变成这个 change 的议题，与"ReAct 工具机制"混成一锅。
**多知识库协同检索留作 V1.0 的独立 change（建议 id：`add-multi-dataset-retrieval`）。**

## Risks / Trade-offs

- [工具结果摘要截断后模型信息不足] → 摘要用于展示，回灌给模型的内容用完整片段，两者分开（展示与推理不共用同一份裁剪逻辑）
- [多轮工具调用导致首字延迟变长] → 沿用现有 `reasoning` 事件思路：工具调用事件必须**先发**，让用户看到"正在检索"
- [消息表结构变更影响既有数据] → 迁移新增列/新消息类型，旧消息按普通消息读取（向前兼容，符合 DSL/数据向前兼容原则）
- [成本上升（多轮模型调用）] → 轮次上限 + 单轮工具结果条数上限，写在配置里而不是常量

## 迁移计划

1. 迁移 `0011_*` 增加工具调用记录承载（新增列或新消息类型），旧数据按原语义读取；
2. 后端先上线链路与事件（前端仍可用旧逻辑忽略未知事件）；
3. 前端再放开形态选择并展示工具块；
4. 回滚：形态选项收回 `chat/rag`，后端保留智能体链路但不被触发。

## Open Questions

- 工具调用的历史记录保留多久（是否随会话删除一起清理）——不影响本次规格与任务拆解，实现时按"随会话删除"处理即可。
